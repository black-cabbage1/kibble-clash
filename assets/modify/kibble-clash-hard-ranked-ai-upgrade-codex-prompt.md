# 멍밥쟁탈전 V1.5 — 어려움 난이도 공식 랭킹 전용화 + AI 난이도 강화 Codex 프롬프트

## 작업 목적

현재 멍밥쟁탈전은 난이도 선택 기능과 Toss 게임센터 리더보드 점수 등록 기능을 가지고 있다.

이번 작업에서는 난이도와 랭킹의 역할을 명확하게 분리한다.

핵심 정책은 다음과 같다.

```text
쉬움  → 일반 플레이
보통  → 일반 플레이
어려움 → 공식 랭킹 참여 가능
```

즉,

**Toss 게임센터 점수 등록은 `어려움` 난이도에서 정상적으로 완료한 게임에서만 가능하도록 제한한다.**

동시에 현재의 `어려움` 난이도는
단순한 이름만 어려운 수준이 아니라
실제로 전략적인 판단을 하는 AI로 체감 난이도를 한 단계 높인다.

---

# 이번 작업의 핵심 목표

1. 어려움 난이도에서만 게임센터 점수 등록 가능
2. 쉬움 / 보통에서는 게임센터 점수 등록 UI와 기능 차단
3. 난이도 선택 화면에서 `어려움 = 공식 랭킹 참여`라는 의미를 명확히 표시
4. 결과 화면에서도 현재 난이도와 랭킹 가능 여부를 명확하게 안내
5. 어려움 AI의 전략 판단 강화
6. AI가 플레이어의 현재 숨겨진 선택을 보고 대응하는 치팅 방식은 금지
7. 쉬움 / 보통의 기존 체감은 최대한 유지
8. 기존 게임센터 연동 및 게임 로직 회귀 방지

---

# 1. 공식 랭킹 등록 조건 변경

게임센터 점수 등록 가능 조건에 다음 조건을 추가한다.

```ts
difficulty === 'hard'
```

실제 프로젝트에서 사용하는 난이도 enum / 상수 / 문자열 값을 먼저 확인하고
기존 구조를 그대로 재사용한다.

예:

```ts
const canSubmitLeaderboard =
  gameCompleted &&
  difficulty === HARD_DIFFICULTY;
```

실제 코드 구조에 맞게 구현하되,
난이도 문자열을 여러 곳에 직접 하드코딩하지 않는다.

---

# 2. 쉬움 / 보통에서는 점수 등록 불가

쉬움 또는 보통 난이도로 게임을 완료하면
Toss 게임센터 점수를 등록할 수 없어야 한다.

## UI 처리

현재 결과 화면에 게임센터 점수 등록 버튼이 있다면:

### 어려움

```text
🏆 랭킹 점수 등록
```

버튼을 정상 노출한다.

### 쉬움 / 보통

점수 등록 버튼을 숨기거나 비활성화한다.

단순 비활성 버튼보다는
등록 버튼 대신 짧은 안내를 보여주는 방향을 우선한다.

예:

```text
🏆 공식 랭킹은 어려움 난이도에서 참여할 수 있어요.
```

### 중요

사용자가 쉬움 / 보통으로 플레이한 뒤
개발자 도구나 내부 함수 호출만으로 게임센터 등록 함수를 실행할 수 없도록
**UI뿐 아니라 실제 submit 로직에서도 난이도 조건을 검증한다.**

즉:

```text
버튼 숨김만 구현하는 것은 불충분
```

반드시 등록 함수 호출 직전에도 조건을 확인한다.

---

# 3. 어려움 난이도 표시 강화

난이도 선택 화면에서
어려움 난이도만 공식 랭킹과 연결된다는 점을 명확하게 보여준다.

권장 예시:

```text
쉬움
가볍게 즐겨요

보통
균형 잡힌 승부

어려움 🏆
전략적인 AI · 공식 랭킹 참여
```

또는 기존 UI 톤에 맞게:

```text
어려움
🏆 공식 랭킹
```

정도의 작은 배지를 추가한다.

### 목표

사용자가 게임 시작 전에:

```text
어려움을 선택하면 랭킹에 기록할 수 있구나.
```

를 이해할 수 있어야 한다.

---

# 4. 어려움 선택 시 랭킹 안내

어려움 난이도를 처음 선택하거나
어려움 난이도 카드가 활성화되었을 때
필요하면 간단한 설명을 제공한다.

예:

```text
🏆 공식 랭킹 모드

어려움 난이도에서 완료한 게임만
게임센터 랭킹에 등록할 수 있어요.
```

### 주의

- 별도의 긴 팝업을 매번 띄우지 않는다.
- 게임 시작을 방해하지 않는다.
- 작은 보조 문구 / 배지 / 최초 1회 안내 정도로 처리한다.
- 기존 난이도 선택 UX를 크게 뜯지 않는다.

---

# 5. 결과 화면 난이도 표시

결과 화면에서도
현재 플레이한 난이도를 확인할 수 있도록 한다.

예:

```text
난이도 · 어려움 🏆
```

또는:

```text
🏆 어려움 · 공식 랭킹
```

쉬움:

```text
난이도 · 쉬움
```

보통:

```text
난이도 · 보통
```

### 이유

점수 등록 가능 / 불가 이유가
결과 화면에서도 자연스럽게 이해되어야 한다.

---

# 6. 기존 점수 등록 조건 보존

현재 프로젝트에 이미 다음과 같은 조건이 있다면 먼저 확인한다.

예:

- 게임 정상 종료 여부
- 결과 화면 진입 여부
- 점수 등록 중복 방지
- 사용자 인증 / Game Center 사용 가능 여부
- 점수 유효성 검사
- 등록 버튼 클릭 여부
- 이미 등록한 점수인지 여부

이번 작업에서는 기존 조건을 제거하지 않는다.

기존 조건에:

```text
어려움 난이도인가?
```

조건만 추가하는 방식으로 구현한다.

---

# 7. 어려움 AI 난이도 강화 — 기본 방향

현재 어려움 난이도를 실제로 한 단계 더 어렵게 만든다.

단,

**AI가 사용자의 현재 선택값을 미리 알고 대응하는 방식은 절대 사용하지 않는다.**

어려움 AI는
현재까지 공개된 게임 상태와 확률 / 기대값을 기반으로
더 좋은 판단을 하는 방향으로 강화한다.

---

# 8. 어려움 AI — 순위별 기대 보상 계산 강화

어려움 AI는
단순히 밥그릇의 1등 보상만 보고 선택하지 않는다.

각 밥그릇의 전체 순위별 보상을 고려한다.

예:

```text
1번 밥그릇

1등 50
2등 20
3등 10
4등 10
```

AI는 대략적으로 다음 요소를 함께 평가해야 한다.

```text
예상 1등 확률 × 1등 보상
+
예상 2등 확률 × 2등 보상
+
예상 3등 확률 × 3등 보상
...
-
CLASH 위험
```

실제 구현은 프로젝트 구조에 맞춰
복잡도를 과도하게 높이지 않는 범위에서 점수화한다.

### 핵심

`가장 큰 1등 보상`만 고르는 AI가 아니라
**기대 획득점수가 높은 선택을 하는 AI**로 만든다.

---

# 9. 어려움 AI — CLASH 위험 적극 반영

어려움 난이도에서는
CLASH 발생 가능성을 보통보다 더 적극적으로 계산한다.

AI가 고려할 수 있는 정보:

- 현재까지 공개된 주사위 배치
- 이미 사용된 숫자
- 남아 있는 선택 가능 숫자
- 각 밥그릇의 경쟁 상태
- 각 밥그릇의 순위별 보상
- 현재 라운드 상황

높은 숫자라도
CLASH 위험이 너무 높으면
안전하게 2등 / 3등 보상을 노리는 선택을 할 수 있어야 한다.

예:

```text
6을 선택하면 50점 가능성이 있지만 CLASH 위험이 큼
4를 선택하면 20점 획득 가능성이 높음
```

이 경우 어려움 AI가
상황에 따라 4를 선택하는 판단을 할 수 있어야 한다.

---

# 10. 어려움 AI — 현재 점수 차이 반영

어려움 AI는
현재 누적 점수 차이와 남은 라운드를 일부 고려한다.

## AI가 앞서고 있는 경우

더 안정적인 선택 비중을 높인다.

예:

- CLASH 위험이 낮은 선택
- 안정적인 2등 / 3등 보상
- 지나치게 큰 도박 회피

## AI가 뒤지고 있는 경우

고득점 가능성이 있는 선택 비중을 높인다.

예:

- 1등 보상이 큰 밥그릇 적극 공략
- 일정 수준의 CLASH 위험 감수
- 기대 변동성이 높은 선택도 고려

### 중요

단순하게:

```text
지고 있으면 항상 6
이기고 있으면 항상 낮은 숫자
```

같은 고정 규칙으로 만들지 않는다.

여러 평가 요소 중 하나의 가중치로 사용한다.

---

# 11. 어려움 AI — 후반 라운드 가중치

게임 후반으로 갈수록
현재 점수 차이의 중요도를 높일 수 있다.

예:

```text
초반:
기대값 중심

후반:
현재 점수 차이 + 기대값 중심
```

마지막 라운드에서는
AI가 현재 승패 상황을 더 적극적으로 반영하도록 한다.

예:

- 근소하게 앞서면 안정적인 선택
- 크게 뒤지면 역전 가능성이 있는 고보상 선택

---

# 12. 어려움 AI — 지나친 완벽 플레이 방지

어려움 AI라고 해서
매 턴 100% 완벽한 최적 선택만 하지 않도록 한다.

권장 방향:

```text
최선 또는 상위권 선택을 높은 확률로 선택
+
소량의 랜덤성 유지
```

예시 개념:

```text
80~90%:
평가 점수가 높은 후보 중 선택

10~20%:
상위 몇 개 후보 중 가중 랜덤 선택
```

정확한 비율은 기존 AI 구조와 플레이 테스트 결과에 따라 조정한다.

### 목표

어려움 AI가:

```text
똑똑하다
```

고 느껴져야 하지만:

```text
매번 수학적으로 완벽하게 움직이는 봇
```

처럼 느껴져서는 안 된다.

---

# 13. 치팅 AI 금지

다음 방식은 사용하지 않는다.

```text
사용자가 이번 턴에 실제 선택한 숫자를 AI가 미리 읽음
```

```text
사용자가 선택한 밥그릇을 AI가 숨겨진 상태에서 미리 확인함
```

```text
AI가 플레이어의 비공개 선택을 보고 정확히 카운터 선택함
```

```text
AI만 주사위 결과를 조작함
```

```text
AI만 보상 계산에서 유리한 예외를 적용함
```

어려움 난이도는
**정보 우위가 아니라 판단력 우위**로 어렵게 만든다.

---

# 14. 공개된 정보만 사용

어려움 AI는
AI가 선택하는 시점에 정상적으로 공개되어 있는 정보만 활용한다.

예:

- 현재 점수
- 현재 라운드
- 공개된 밥그릇 보상
- 이미 배치된 주사위
- 이미 공개된 선택
- 현재 사용 가능한 AI 자신의 선택지

게임 규칙상 아직 공개되지 않은 정보는 사용하지 않는다.

---

# 15. 플레이어 행동 패턴 반영 — 선택적 적용

현재 구조에서 지나친 개발 복잡도를 만들지 않는다면
어려움 AI가 **현재 한 게임 안에서만**
플레이어의 이전 선택 성향을 약하게 반영할 수 있다.

예:

- 높은 숫자를 자주 고르는 편인지
- 고보상 밥그릇을 자주 노리는지
- 빈 밥그릇을 선호하는지
- CLASH 위험을 자주 감수하는지

단,

이 기능은 필수 구현이 아니다.

기존 AI 구조를 크게 복잡하게 만들거나
버그 가능성을 높인다면 제외한다.

우선순위는:

```text
기대 보상 계산
→ CLASH 위험
→ 점수 차이
→ 후반 전략
```

이다.

---

# 16. 쉬움 / 보통은 기존 체감 유지

이번 작업의 주 대상은 `어려움`이다.

쉬움 / 보통의 AI는
현재 플레이 체감을 최대한 유지한다.

### 쉬움

현재 초보자용 성격 유지.

### 보통

현재 일반 난이도 성격 유지.

AI 공통 모듈을 리팩터링해야 한다면
쉬움 / 보통의 행동 확률과 결과가 크게 바뀌지 않도록 회귀 테스트한다.

# 17. 난이도별 역할 정리

최종적으로 다음 느낌이 명확하게 구분되어야 한다.

## 쉬움

```text
가볍게 즐기는 모드
초보자 친화적 AI
랭킹 등록 불가
```

## 보통

```text
기본적인 전략 플레이
균형 잡힌 AI
랭킹 등록 불가
```

## 어려움

```text
전략 판단 강화
CLASH 위험 적극 계산
점수 상황에 따른 대응
공식 랭킹 참여 가능
```

# 18. 랭킹 등록 UX 권장안

어려움 난이도 결과 화면:

```text
🏆 공식 랭킹

어려움 난이도 기록

[ 랭킹 점수 등록 ]
```

쉬움 / 보통 결과 화면:

```text
🏆 공식 랭킹은
어려움 난이도에서 참여할 수 있어요.
```

필요하면 보조 CTA:

```text
어려움으로 도전
```

을 제공할 수 있으나
기존 결과 화면이 복잡해진다면 추가하지 않는다.

---

# 19. 중복 점수 등록 방지

기존에 점수 중복 제출 방지 로직이 있다면 유지한다.

없다면 현재 구조를 확인하고
한 게임의 결과가 반복 클릭으로 여러 번 제출되지 않도록 한다.

예:

```ts
isSubmitting
hasSubmittedLeaderboardScore
```

등 현재 패턴에 맞게 처리한다.

단, 이번 작업 때문에 새로운 복잡한 서버 상태 시스템을 만들 필요는 없다.

---

# 20. 난이도 변경 후 등록 우회 방지

게임 시작 시 선택한 난이도를
해당 게임 세션에 고정한다.

예:

```ts
gameSession.difficulty
```

결과 화면에서 설정값을 바꾸거나
전역 난이도 설정을 변경한 뒤
쉬움 게임을 어려움으로 위장하여 등록할 수 없어야 한다.

점수 등록 조건은
**현재 설정 화면의 난이도 값이 아니라
해당 게임을 실제로 시작할 때 확정된 난이도 값**을 기준으로 판정한다.

이 부분은 반드시 확인한다.

---

# 21. 기존 Toss 게임센터 연동 유지

현재 구현되어 있는
Toss 게임센터 점수 등록 API 호출 방식은 유지한다.

이번 작업에서
별도의 자체 랭킹 서버나 난이도별 커스텀 리더보드를 만들지 않는다.

즉:

```text
Toss 게임센터 리더보드 1개
+
어려움에서만 점수 등록
```

구조로 유지한다.

기존 Game Center 초기화 / 등록 / 오류 처리 코드를 먼저 확인하고
불필요하게 다시 작성하지 않는다.

---

# 22. 게임센터 등록 실패 처리

어려움 난이도에서 등록 조건을 만족했더라도
게임센터 API 호출이 실패할 수 있다.

기존 오류 처리 UX가 있다면 유지한다.

없다면 최소한:

```text
점수를 등록하지 못했어요.
잠시 후 다시 시도해주세요.
```

정도의 사용자 안내를 제공한다.

단,
API 실패를 게임 패배나 게임 결과 실패처럼 처리하지 않는다.

---

# 23. 난이도 표기 일관성

앱 전체에서 난이도 명칭을 통일한다.

```text
쉬움
보통
어려움
```

`Hard`, `랭크`, `랭킹 난이도` 등
여러 이름을 혼용하지 않는다.

공식 랭킹 여부는 배지로 보조한다.

예:

```text
어려움 🏆
```

---

# 24. UI 과밀 방지

랭킹 관련 설명을 추가하면서
난이도 선택 화면이나 결과 화면이 과밀해지지 않도록 한다.

핵심 정보는:

```text
어려움
전략적인 AI
🏆 공식 랭킹
```

정도만 빠르게 읽히면 된다.

긴 설명은 피한다.

---

# 25. 밸런스 조정은 수치 분리

어려움 AI 관련 가중치 / 확률을
가능한 한 한 곳에서 관리할 수 있도록 한다.

예:

```ts
HARD_AI_CONFIG = {
  clashRiskWeight: ...,
  rewardExpectationWeight: ...,
  scoreGapWeight: ...,
  lateRoundWeight: ...,
  randomness: ...
}
```

실제 프로젝트의 구조에 맞게 적용한다.

### 목적

향후 통합 QA / 밸런스 조정에서
수치를 쉽게 변경할 수 있어야 한다.

AI 알고리즘 내부 곳곳에 매직넘버를 흩뿌리지 않는다.

---

# 26. 디버그 / 테스트 가능성

개발 환경에서
어려움 AI가 어떤 판단을 했는지 확인하기 쉽게 만든다.

필요하면 개발 모드에서만:

```text
candidate score
clash risk
expected reward
score-gap modifier
final decision
```

등을 console/debug 정보로 확인할 수 있게 한다.

### 중요

프로덕션 UI에는 표시하지 않는다.

# 최종 QA 체크리스트

## 랭킹 조건

- [ ] 쉬움 난이도에서는 게임센터 점수 등록이 불가능하다.
- [ ] 보통 난이도에서는 게임센터 점수 등록이 불가능하다.
- [ ] 어려움 난이도에서는 기존 조건을 만족하면 점수 등록이 가능하다.
- [ ] UI뿐 아니라 submit 함수에서도 난이도를 검증한다.
- [ ] 쉬움 / 보통에서 등록 함수를 우회 호출해도 막힌다.
- [ ] 게임 시작 시 확정된 난이도를 기준으로 등록 여부를 판정한다.
- [ ] 결과 화면에서 난이도를 바꿔 등록 조건을 우회할 수 없다.

## 난이도 선택 UI

- [ ] 어려움에 공식 랭킹 배지가 보인다.
- [ ] 쉬움 / 보통이 랭킹 대상이 아니라는 것이 혼동되지 않는다.
- [ ] UI가 과밀해지지 않았다.
- [ ] 작은 모바일 화면에서 문구가 깨지지 않는다.

## 결과 화면

- [ ] 어려움 결과에는 랭킹 등록 CTA가 정상 노출된다.
- [ ] 쉬움 / 보통에는 공식 랭킹 안내가 적절히 표시된다.
- [ ] 현재 플레이한 난이도가 표시된다.
- [ ] 등록 완료 후 중복 제출되지 않는다.
- [ ] 등록 실패 시 기존 또는 적절한 오류 안내가 나온다.

## 어려움 AI

- [ ] 순위별 보상을 고려한다.
- [ ] 1등 보상만 단순 비교하지 않는다.
- [ ] CLASH 위험을 보통보다 적극적으로 고려한다.
- [ ] 안전한 2등 / 3등 선택을 할 수 있다.
- [ ] 현재 점수 차이를 전략에 반영한다.
- [ ] 후반 라운드에서 점수 차이의 중요도가 높아진다.
- [ ] 뒤지고 있을 때 역전을 노리는 선택이 가능하다.
- [ ] 앞서고 있을 때 안정적인 선택이 가능하다.
- [ ] 매번 완벽한 동일 선택만 하지 않는다.
- [ ] 일정 수준의 랜덤성이 남아 있다.

## 치팅 방지

- [ ] 사용자의 비공개 현재 선택값을 AI가 읽지 않는다.
- [ ] 사용자의 숨겨진 밥그릇 선택을 미리 읽지 않는다.
- [ ] AI 주사위만 조작하지 않는다.
- [ ] AI에만 유리한 점수 예외가 없다.
- [ ] AI 의사결정 시점에 공개된 정보만 사용한다.

## 회귀 테스트

- [ ] 쉬움 AI 체감이 크게 변하지 않았다.
- [ ] 보통 AI 체감이 크게 변하지 않았다.
- [ ] 게임 시작 / 진행 / 결과 흐름이 정상이다.
- [ ] CLASH 계산이 기존과 동일하다.
- [ ] 점수 계산이 기존과 동일하다.
- [ ] 포인트 보상이 기존과 동일하다.
- [ ] Game Center 기존 연동이 정상 작동한다.
- [ ] 튜토리얼 흐름에 영향이 없다.
- [ ] 모바일 레이아웃이 깨지지 않는다.
