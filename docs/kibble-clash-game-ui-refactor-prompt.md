# 멍밥쟁탈전 게임 진행 화면 UI/UX 개선 프롬프트

## 0. 작업 목적

현재 구현된 게임 진행 화면은 규칙과 턴 진행은 동작하지만, 시각적으로는 게임보다 관리용 대시보드에 가깝다.

이번 작업의 목표는 **기존 게임 로직을 유지하면서 게임 진행 화면을 귀엽고 직관적인 강아지 보드게임 UI로 재설계하는 것**이다.

화려한 최종 일러스트를 완성하는 단계는 아니다.

우선 다음을 달성한다.

- 게임판처럼 보이는 화면
- 한눈에 이해되는 정보 위계
- 강아지 캐릭터가 중심이 되는 구성
- 주사위 선택과 밥그릇 배치의 명확한 연결
- 동률 상쇄가 대표 이벤트로 느껴지는 연출
- 모바일 가로 화면에서 읽기 쉬운 구조

---

# 1. 현재 화면 참고

현재 구현 화면을 다음 경로에 둘 수 있다.

```text
docs/reference/current-game-screen.png
```

현재 화면의 주요 구조:

- 상단에 라운드, 현재 턴, 플레이어 4명 정보
- 중앙에 2×3 형태의 밥그릇 6개
- 각 밥그릇마다 플레이어 4명 배치 수를 표 형태로 반복 표시
- 하단에 현재 주사위 결과와 선택 버튼
- 어두운 대시보드 스타일

현재 구현을 삭제하거나 게임 로직을 새로 만들지 말고, 기존 컴포넌트와 상태 흐름을 먼저 분석한 뒤 프레젠테이션 레이어를 개선한다.

---

# 2. 절대 변경하지 않을 것

이번 작업에서는 다음 게임 규칙과 데이터 흐름을 변경하지 않는다.

- 총 4라운드
- 사용자 1명과 AI 3명
- 플레이어별 주사위 8개
- 남은 주사위를 모두 굴림
- 나온 숫자 중 하나 선택
- 선택한 눈의 주사위를 해당 번호 밥그릇에 전부 배치
- 밥그릇마다 라운드 시작 전에 사료 보상 카드 공개
- 보상 합계가 최소 기준 이상이 될 때까지 카드 배치
- 같은 개수로 배치한 플레이어 동률 상쇄
- 상쇄 후 살아남은 순위대로 큰 보상 카드부터 한 장씩 획득
- 라운드 정산
- 최종 점수 계산
- 기존 AI 로직
- 기존 테스트
- 기존 게임 상태 모델

UI 개선 과정에서 도메인 로직, 정산 규칙, 점수 계산을 임의로 수정하지 않는다.

# 3. 현재 화면의 문제

## 3.1 대시보드처럼 보인다

현재 밥그릇 6개가 모두 큰 카드 안에 들어가 있고, 각 카드에서 플레이어 4명의 행이 반복된다.

결과적으로 화면이 다음처럼 느껴진다.

- 관리 도구
- 데이터 테이블
- 운영 대시보드
- 게임 개발자용 디버그 패널

사용자가 실제 보드게임을 플레이한다는 느낌이 약하다.

## 3.2 강아지 테마가 약하다

강아지 정보가 상단 작은 이름표에만 있고, 게임판 중앙에서는 캐릭터의 존재감이 거의 없다.

주인공인 진도믹스와 AI 캐릭터인 푸들, 퍼그, 골든리트리버가 실제로 밥그릇을 두고 경쟁하는 느낌이 나야 한다.

## 3.3 핵심 행동보다 정보 표가 먼저 보인다

사용자의 한 턴은 단순하다.

```text
주사위 확인
→ 숫자 하나 선택
→ 해당 밥그릇에 전부 놓기
```

하지만 현재 화면에서는 밥그릇별 반복 표를 읽는 일이 더 크게 느껴진다.

## 3.4 빈 공간이 비주얼 역할을 하지 못한다

각 밥그릇 카드 내부의 큰 빈 사각형은 실제 밥그릇, 사료 보상, 배치 토큰을 보여주는 공간으로 사용되어야 한다.

## 3.5 상쇄가 핵심 이벤트처럼 느껴지지 않는다

`동률 상쇄`는 이 게임의 대표 재미이지만 현재 UI에서는 단순 정산 결과에 가까워 보인다.

상쇄가 일어나는 순간은 시각적으로 기억에 남아야 한다.

# 4. 목표 화면 방향

## 핵심 문장

> 6개의 밥그릇을 중심으로 네 마리 강아지가 사료를 두고 눈치싸움을 벌이는 귀여운 전략 보드게임 화면

## 시각적 목표

- 데이터 카드가 아니라 실제 보드판처럼 보일 것
- 밥그릇 6개가 화면의 주인공일 것
- 플레이어 배치 수는 표가 아니라 캐릭터 토큰으로 표시할 것
- 사용자가 지금 해야 할 행동을 1초 안에 이해할 수 있을 것
- 현재 턴과 선택 가능한 숫자를 강하게 강조할 것
- 색상만으로 팀을 구분하지 않을 것
- 완성 일러스트가 없어도 CSS, 도형, 간단한 SVG, 플레이스홀더로 게임 분위기를 만들 것

# 5. 새로운 전체 레이아웃

가로형 모바일 화면을 기준으로 다음 구조를 우선 검토한다.

```text
┌─────────────────────────────────────────────────────────┐
│ 라운드 · 현재 턴 · 메뉴                                │
├─────────────────────────────────────────────────────────┤
│ 플레이어 4명 상태 바                                   │
├─────────────────────────────────────────────────────────┤
│                                                         │
│                 2×3 밥그릇 게임판                       │
│                                                         │
├─────────────────────────────────────────────────────────┤
│ 현재 굴림 결과 · 숫자 선택 · 행동 안내                │
└─────────────────────────────────────────────────────────┘
```

화면 높이가 부족하면 플레이어 상태 바를 더 컴팩트하게 만들되, 중앙 게임판과 하단 행동 영역은 항상 충분한 공간을 확보한다.

---

# 6. 상단 영역 개선

## 6.1 라운드와 현재 턴

현재처럼 작은 배지로 분산시키지 말고 한 영역에서 명확하게 보여준다.

예시:

```text
ROUND 1 / 4
지금은 진도믹스 차례!
남은 주사위 8개
```

요구사항:

- 현재 턴 플레이어의 캐릭터 얼굴 또는 플레이스홀더 아이콘 표시
- 현재 해야 할 행동을 함께 안내
- 현재 턴 플레이어의 팀 색상과 문양을 사용
- 지나치게 큰 세로 공간을 사용하지 않음
- `게임 나가기`는 주요 행동과 떨어진 보조 위치에 둠
- 나가기 버튼이 게임 행동보다 시각적으로 강하지 않게 함

## 6.2 플레이어 상태 바

각 플레이어는 다음 정보만 기본 표시한다.

- 캐릭터 얼굴
- 이름
- 현재 총점
- 남은 주사위 수
- 현재 턴 여부

추천 캐릭터:

- 사용자: 진도믹스
- AI 1: 푸들
- AI 2: 퍼그
- AI 3: 골든리트리버

구분 방식:

- 진도믹스: 파랑 + 마름모 또는 뼈다귀 문양
- 푸들: 분홍 + 원 또는 리본 문양
- 퍼그: 노랑 + 삼각형 또는 간식 문양
- 골든리트리버: 초록 + 사각형 또는 발바닥 문양

색상, 캐릭터, 문양, 이름을 동시에 제공한다.

# 7. 중앙 밥그릇 게임판 개선

## 7.1 2×3 배치 유지

6개 밥그릇은 현재처럼 2행 3열로 배치한다.

다만 각 항목을 `정보 카드`가 아니라 `보드판의 구역`처럼 표현한다.

## 7.2 밥그릇 한 칸의 기본 구조

각 밥그릇은 다음 요소로 구성한다.

```text
┌──────────────────────────┐
│ ① 밥그릇      총 50점    │
│ [20] [20] [10]           │
│                          │
│       밥그릇 비주얼       │
│                          │
│ 진도믹스 ×2   푸들 ×1    │
│ 퍼그 ×0       리트리버 ×1│
└──────────────────────────┘
```

하지만 실제 UI에서는 플레이어 정보를 네 줄짜리 표로 만들지 않는다.

## 7.3 보상 표현

상단에 다음을 표시한다.

- 밥그릇 번호
- 총 사료 포인트
- 개별 보상 카드

예시:

```text
3번 밥그릇
총 60점
[30] [20] [10]
```

보상 카드는 작은 사료 봉지, 캔, 간식 상자 모양의 플레이스홀더로 표현할 수 있다.

MVP에서는 카드 숫자가 가장 명확하게 보여야 한다.

## 7.4 밥그릇 비주얼

현재의 `BOWL 1` 빈 상자를 제거한다.

대신 다음 중 하나를 구현한다.

- CSS로 만든 간단한 밥그릇
- SVG 밥그릇
- 원형 또는 타원형 플레이스홀더
- 번호가 표시된 컬러 밥그릇

최종 아트가 없어도 실제 게임판처럼 보여야 한다.

밥그릇 주변에는 현재 배치된 플레이어 토큰을 놓는다.

## 7.5 플레이어 배치 표시

현재처럼 플레이어 4명의 전체 행을 반복하지 않는다.

대신 각 플레이어를 작은 토큰으로 표시한다.

예시:

```text
[진도믹스 얼굴] ×3
[푸들 얼굴] ×2
[퍼그 얼굴] ×2
```

배치 수가 0인 플레이어는 다음 중 하나로 처리한다.

- 아예 표시하지 않음
- 매우 약한 비활성 토큰으로 표시
- 선택한 밥그릇 상세 영역에서만 표시

기본 게임판에는 실제로 배치된 플레이어만 보여주는 방식을 우선 검토한다.

## 7.6 현재 우세와 동률 상태

각 밥그릇에서 현재 상태를 빠르게 알 수 있게 한다.

예시 상태:

- `진도믹스 우세`
- `푸들·퍼그 동률 위험`
- `아직 비어 있음`

동률인 토큰은 연결선, 충돌 아이콘 또는 `!` 표시로 보여줄 수 있다.

단, 현재 정산 결과가 확정된 것처럼 오해시키지 말고 `현재 기준 예상`임을 드러낸다.

# 8. 하단 주사위 행동 영역 개선

이 영역은 사용자가 실제로 조작하는 핵심 영역이므로 가장 명확해야 한다.

## 8.1 현재 굴림 결과

현재 텍스트 나열만 보여주지 말고 실제 주사위 또는 숫자 타일로 표현한다.

예시:

```text
⚄  ⚁  ⚃  ⚀  ⚄  ⚅  ⚅  ⚃
```

접근성을 위해 실제 텍스트 값도 함께 제공한다.

## 8.2 선택 가능한 숫자

숫자별로 묶어 다음처럼 표시한다.

```text
[1]
1개 전부 놓기

[2]
1개 전부 놓기

[4]
2개 전부 놓기

[5]
2개 전부 놓기

[6]
2개 전부 놓기
```

요구사항:

- 존재하지 않는 숫자는 표시하지 않음
- 선택 버튼에는 숫자와 주사위 개수를 모두 표시
- 버튼을 누르기 전 현재 행동 결과가 명확해야 함
- 일부만 배치할 수 없다는 규칙을 문구로 전달
- 터치 영역을 충분히 크게 확보

## 8.3 숫자 선택과 밥그릇 연결

사용자가 `4` 버튼을 탭하거나 포커스하면:

- 4번 밥그릇을 하이라이트
- 배치 예정 토큰 수를 미리 표시
- 다른 밥그릇은 약하게 처리
- 예상 상태 변화를 보여줌

예시:

```text
4번 밥그릇에 진도믹스 주사위 2개를 놓습니다.
```

가능하면 1단계 선택 후 확인 버튼을 두지 않고 한 번 탭으로 배치하되, 실수 방지를 위해 짧은 배치 애니메이션과 명확한 피드백을 제공한다.

# 9. 동률 상쇄 연출

상쇄는 이 게임의 대표 이벤트다.

## 9.1 발생 시점

라운드 정산 화면 또는 밥그릇별 순차 정산에서 상쇄를 보여준다.

## 9.2 기본 연출

최종 일러스트 없이도 다음 순서로 구현한다.

1. 동률 플레이어 토큰 흔들림
2. 해당 토큰 사이에 충돌 아이콘 표시
3. `KIBBLE CLASH!` 또는 `동률 상쇄!` 표시
4. 토큰이 흐려지거나 화면 밖으로 튕겨 나감
5. 살아남은 순위 토큰 강조
6. 보상 카드가 획득 플레이어 쪽으로 이동

화면 전체를 과도하게 흔들지 않는다.

## 9.3 텍스트 피드백

애니메이션만으로 결과를 전달하지 않는다.

예시:

```text
푸들과 퍼그가 3개로 동률!
두 팀 모두 상쇄되었습니다.

진도믹스가 30점 사료를 획득했습니다.
골든리트리버가 20점 사료를 획득했습니다.
```

## 9.4 건너뛰기

- 정산 연출 건너뛰기
- 동작 줄이기 설정
- 애니메이션이 끝나지 않아도 게임 상태는 이미 확정되어 있어야 함
- 연출 중 재입력으로 상태가 중복 변경되지 않도록 함

# 10. 비주얼 스타일

## 10.1 현재 어두운 대시보드 톤 완화

완전한 최종 아트를 만들 필요는 없지만, 다음 분위기를 적용한다.

- 따뜻한 베이지 또는 우드 보드
- 잔디 또는 마당을 연상시키는 배경
- 컬러 밥그릇
- 사료 카드
- 발바닥 문양
- 둥근 모서리
- 캐주얼 게임다운 버튼

다크 모드를 유지한다면 중앙 게임판만큼은 따뜻한 재질과 색을 사용한다.

## 10.2 우선순위

다음 순서로 디자인한다.

1. 가독성
2. 상태 이해
3. 조작 명확성
4. 강아지 테마
5. 장식

장식 때문에 숫자, 토큰 수, 보상 카드가 읽히지 않으면 안 된다.

## 10.3 플레이스홀더

최종 캐릭터 이미지가 없으면 다음을 사용한다.

- 원형 캐릭터 아바타
- 품종명 첫 글자
- 간단한 강아지 얼굴 SVG
- 색상 + 문양 토큰

외부 이미지를 임의로 다운로드하지 않는다.

---

# 11. 반응형 기준

## 주요 목표 해상도

- 모바일 가로 화면
- 16:9 비율 우선
- 더 좁거나 낮은 화면에서도 주요 행동이 잘리지 않아야 함

## 요구사항

- Safe Area 고려
- 내부 화면 전체 세로 스크롤은 되도록 피함
- 밥그릇 6개가 한 화면에 유지되도록 구성
- 하단 행동 영역이 화면 밖으로 밀리지 않음
- 텍스트가 지나치게 작아지지 않음
- 해상도가 낮을 때 장식 요소를 먼저 축소
- 플레이어 이름이 길면 말줄임 처리하되 접근 가능한 이름 유지

---

# 12. 접근성 요구사항

- 팀을 색상만으로 구분하지 않음
- 캐릭터, 이름, 문양, 색상을 함께 사용
- 모든 버튼에 명확한 접근 가능한 이름 제공
- 예: `숫자 4, 주사위 2개를 4번 밥그릇에 전부 놓기`
- 현재 턴 변경을 텍스트로 알림
- 주사위 결과를 숫자 텍스트로 제공
- 상쇄 결과를 텍스트로도 제공
- 선택 상태를 색상 외에 테두리, 아이콘, 문구로 표시
- 충분한 명도 대비 확보
- 터치 대상 크기 확보
- 애니메이션 건너뛰기 및 동작 줄이기 고려
- 게임 상태가 스크린리더 읽기 순서상 논리적으로 배치되도록 구성

# 13. 구현 방식

## 13.1 먼저 분석

코드를 수정하기 전에 다음을 확인한다.

- 현재 게임 화면 컴포넌트 구조
- 상태 관리 방식
- 밥그릇 데이터 모델
- 플레이어 배치 데이터
- 주사위 선택 이벤트
- 라운드 정산 이벤트
- 기존 CSS 또는 Cocos UI 구조
- 재사용 가능한 컴포넌트

분석 결과를 간단히 보고한 뒤 작업한다.

## 13.2 프레젠테이션 레이어 중심

가능하면 다음처럼 컴포넌트를 분리한다.

```text
GameScreen
├─ RoundTurnHeader
├─ PlayerStatusBar
├─ BowlBoard
│  └─ BowlZone × 6
│     ├─ RewardCards
│     ├─ BowlVisual
│     ├─ PlayerTokens
│     └─ BowlStatus
├─ RollActionPanel
│  ├─ DiceResults
│  └─ NumberChoiceButton
└─ ClashOverlay
```

도메인 상태를 UI에 맞추기 위해 별도의 ViewModel을 사용할 수 있다.

## 13.3 상태 모델을 UI 때문에 변경하지 말 것

UI가 불편하다는 이유로 게임 상태 모델을 중복 생성하거나 게임 규칙을 프레젠테이션 컴포넌트에 복사하지 않는다.

정산 계산은 기존 도메인 로직을 사용한다.

## 13.4 임시 연출

애니메이션 라이브러리를 새로 추가하기 전에 기본 기능으로 구현한다.

- CSS transition
- Cocos Tween
- opacity
- scale
- position
- 간단한 SVG

프로젝트 환경에 맞는 기본 방식을 사용한다.

# 15. 완료 기준

다음을 만족해야 이번 UI 개선이 완료된 것으로 본다.

## 화면

- 중앙 화면이 대시보드가 아니라 보드게임판처럼 보인다.
- 6개의 밥그릇이 게임 화면의 중심으로 보인다.
- 각 밥그릇의 보상 카드가 한눈에 읽힌다.
- 네 줄짜리 플레이어 표가 반복되지 않는다.
- 배치된 플레이어가 캐릭터 토큰과 개수로 표시된다.
- 주인공 진도믹스와 AI 캐릭터의 존재감이 있다.
- 현재 턴과 해야 할 행동이 즉시 보인다.
- 하단 주사위 선택 영역이 주요 액션으로 보인다.

## 상호작용

- 숫자 선택 시 해당 밥그릇이 명확하게 강조된다.
- 몇 개의 주사위가 배치되는지 미리 알 수 있다.
- 배치 후 보드 상태가 즉시 갱신된다.
- 동률 상쇄가 시각적·텍스트 방식으로 전달된다.
- 연출이 게임 상태를 중복 변경하지 않는다.

## 기술

- 기존 게임 규칙이 변경되지 않는다.
- 기존 자동 테스트가 통과한다.
- 새 UI 관련 테스트가 필요한 경우 추가한다.
- 타입 오류가 없다.
- 빌드가 성공한다.
- 주요 모바일 가로 해상도에서 화면이 잘리지 않는다.
- 접근성 요구사항을 가능한 범위에서 반영한다.
