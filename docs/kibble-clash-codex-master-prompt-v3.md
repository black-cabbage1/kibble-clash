# 멍밥쟁탈전(Kibble Clash) — Codex 게임 개발 마스터 프롬프트

## 0. 역할

당신은 다음 역량을 가진 시니어 개발자다.

- Cocos Creator 3.x 기반 2D 모바일 게임 개발
- TypeScript 게임 도메인 로직 설계
- Apps in Toss 미니게임 연동 및 출시 준비
- 테스트 가능한 아키텍처와 단계적 프로토타이핑
- 모바일 UX, 성능, 접근성을 고려한 캐주얼 게임 제작

이 프로젝트의 목표는 최종 상용 버전을 한 번에 만드는 것이 아니다.

**첫 번째 목표는 실제로 한 판을 끝까지 플레이할 수 있고, 핵심 재미를 검증할 수 있는 그레이박스 MVP를 만드는 것**이다.

화려한 그래픽, 광고, 결제, 리더보드, 캐릭터 성장 등은 핵심 게임이 재미있다는 사실을 확인한 뒤 추가한다.

# 2. 게임 콘셉트

강아지 네 마리가 여러 밥그릇을 두고 사료를 모으는 짧은 전략 게임이다.

사용자는 주사위를 굴려 나온 숫자 중 하나를 선택하고, 같은 숫자의 주사위를 해당 밥그릇에 모두 배치한다.

각 밥그릇에서 가장 높은 영향력을 확보한 강아지가 사료 보상을 얻는다. 다만 같은 영향력으로 맞붙은 강아지들은 서로 상쇄되어 해당 순위에서 제외된다.

핵심 재미는 다음 세 가지다.

1. 큰 보상이 있는 밥그릇에 집중할지 안전한 밥그릇을 선택할지 판단
2. 상대와 동률을 만들어 함께 탈락시킬지 판단
3. 남은 주사위와 상대의 배치를 보고 마지막 역전을 노리는 눈치싸움

게임은 귀엽고 가족 친화적인 분위기여야 한다.

카지노, 도박, 베팅, 현금, 잭팟 등의 표현은 사용하지 않는다.

# 4. MVP 게임 규칙

아래 규칙은 재미 검증을 위한 임시 규칙이다. 숫자와 보상 값은 데이터 파일에서 쉽게 변경 가능하도록 구현한다.

## 기본 구성

- 플레이어: 사용자 1명 + AI 3명
- 밥그릇: 6개
- 밥그릇 번호: 1~6
- 경기 라운드: 2라운드
- 각 플레이어의 라운드 시작 주사위: 6개
- 주사위 눈: 1~6
- 시작 플레이어는 라운드마다 순환

## 한 턴의 흐름

1. 현재 플레이어가 남아 있는 주사위를 모두 굴린다.
2. 나온 숫자들을 눈별 개수로 표시한다.
3. 플레이어는 나온 숫자 중 하나를 선택한다.
4. 선택한 숫자의 주사위를 해당 번호 밥그릇에 전부 배치한다.
5. 배치한 주사위는 해당 라운드 동안 다시 사용하지 않는다.
6. 남은 주사위가 있으면 다음 자기 차례에 다시 굴린다.
7. 주사위가 없으면 이후 차례를 건너뛴다.
8. 모든 플레이어가 주사위를 모두 사용하면 라운드를 정산한다.

## 라운드 시작 전 사료 보상 배정

**주사위를 굴리기 전에 1~6번 밥그릇 각각에 이번 라운드에서 획득할 수 있는 사료 보상 카드를 무작위로 배치하고, 모든 플레이어에게 공개한다.**

플레이어는 각 밥그릇의 보상 구성과 총량을 확인한 뒤 어느 밥그릇에 주사위를 투입할지 결정한다.

핵심 흐름은 다음과 같다.

```text
사료 보상 카드 공개
→ 남은 주사위 전부 굴리기
→ 숫자 하나 선택
→ 같은 숫자의 주사위 전부 배치
→ 모든 주사위 소진
→ 동률 상쇄
→ 순위별 사료 보상 정산
```

### 사료 보상 덱

MVP에서는 사료 보상을 숫자가 적힌 카드 또는 토큰으로 표현한다.

예시 보상 값:

```ts
[10, 20, 30, 40, 50]
```

실제 카드 구성과 장수는 `game-config.ts`에서 변경할 수 있어야 한다.

추후 그래픽에서는 같은 점수라도 다음처럼 다른 사료 종류로 표현할 수 있다.

- 건식사료 봉지
- 습식사료 캔
- 간식 상자

하지만 MVP에서는 음식 종류에 별도 능력을 부여하지 않고, 카드에 적힌 숫자를 모두 동일한 `사료 포인트`로 계산한다.

### 밥그릇별 보상 배치 규칙

각 라운드 시작 시 사료 보상 덱을 섞고, 1번 밥그릇부터 6번 밥그릇까지 차례로 보상 카드를 배치한다.

각 밥그릇에는 **보상 합계가 최소 50포인트 이상이 될 때까지** 카드를 계속 공개해 놓는다.

예시:

```text
1번 밥그릇
- 30포인트 카드 공개
- 아직 50 미만이므로 20포인트 추가
- 총 50포인트 → 배치 완료

2번 밥그릇
- 40포인트 카드 공개
- 아직 50 미만이므로 30포인트 추가
- 총 70포인트 → 배치 완료
```

요구사항:

- 매 라운드 시작 시 보상 덱을 Seeded RNG로 섞는다.
- 각 밥그릇은 총보상이 최소 기준 이상이 될 때까지 카드를 받는다.
- 기본 최소 기준은 `50`이며 설정 파일에서 변경 가능해야 한다.
- 카드 배치가 끝난 뒤 모든 밥그릇의 카드 목록과 총보상을 공개한다.
- 주사위 배치가 시작된 뒤 해당 라운드의 보상 구성은 바뀌지 않는다.
- 다음 라운드가 시작되면 사용한 보상 카드를 정리하고 새로 배치한다.
- 보상 덱이 부족해질 경우의 처리 방식을 명시적으로 구현한다.
  - 기본안: 사용한 카드를 섞어 새 덱으로 만들고 계속 진행
- 동일한 시드에서는 동일한 보상 배치가 재현되어야 한다.

## 기본 구성

- 플레이어: 사용자 1명 + AI 3명
- 밥그릇: 6개
- 밥그릇 번호: 1~6
- 경기 라운드: 4라운드
- 각 플레이어의 라운드 시작 주사위: 8개
- 주사위 눈: 1~6
- 시작 플레이어는 라운드마다 시계 방향으로 순환

## 한 턴의 흐름

1. 현재 플레이어가 아직 배치하지 않은 자신의 주사위를 모두 굴린다.
2. 나온 주사위 눈을 1~6별 개수로 표시한다.
3. 플레이어는 나온 숫자 중 하나만 선택한다.
4. 선택한 숫자의 주사위를 해당 번호의 밥그릇에 전부 배치한다.
5. 같은 숫자의 주사위 중 일부만 배치할 수 없다.
6. 배치한 주사위는 해당 라운드 동안 다시 굴리지 않는다.
7. 남아 있는 주사위가 있으면 다음 사람에게 턴을 넘긴다.
8. 남은 주사위가 없는 플레이어는 이후 차례를 건너뛴다.
9. 모든 플레이어가 주사위 8개를 전부 배치하면 라운드를 정산한다.

### 턴 예시

```text
굴린 결과:
1, 1, 3, 5, 5, 5, 6, 6
```

사용자가 `5`를 선택하면 5번 밥그릇에 주사위 3개를 전부 배치해야 한다.

`5` 주사위 중 1개나 2개만 배치할 수 없다.

## 밥그릇 정산 — 동률 상쇄와 순위별 보상

모든 플레이어가 주사위를 전부 배치하면 1번 밥그릇부터 6번 밥그릇까지 순서대로 정산한다.

### 1. 동률 상쇄

특정 밥그릇에 같은 개수의 주사위를 놓은 플레이어가 둘 이상 있으면, 해당 플레이어들은 모두 그 밥그릇의 정산 대상에서 제외된다.

여러 개의 동률 집단이 있으면 각각 모두 상쇄한다.

예시:

```text
진도믹스: 3개
푸들: 3개
퍼그: 1개
골든리트리버: 0개
```

진도믹스와 푸들은 3개로 동률이므로 둘 다 상쇄된다.

퍼그만 살아남아 1위가 된다.

### 2. 살아남은 플레이어 순위 결정

동률 상쇄 후 남은 플레이어를 주사위 수가 많은 순서로 정렬한다.

예시:

```text
진도믹스: 4개
푸들: 3개
퍼그: 3개
골든리트리버: 1개
```

푸들과 퍼그는 상쇄된다.

남은 순위:

```text
1위: 진도믹스 4개
2위: 골든리트리버 1개
```

### 3. 사료 보상 지급

밥그릇에 놓인 사료 보상 카드를 숫자가 큰 순서대로 정렬한다.

동률 상쇄 후 살아남은 플레이어도 주사위 수가 많은 순서대로 정렬한다.

그다음 다음 규칙으로 한 장씩 지급한다.

```text
1위 플레이어 → 가장 큰 사료 보상 카드 1장
2위 플레이어 → 그다음으로 큰 사료 보상 카드 1장
3위 플레이어 → 그다음 카드 1장
```

한 플레이어가 한 밥그릇에서 여러 장을 가져가지는 않는다.

### 정산 예시

```text
3번 밥그릇 보상:
30포인트, 20포인트, 10포인트

배치 결과:
진도믹스 4개
푸들 3개
퍼그 3개
골든리트리버 1개
```

푸들과 퍼그는 동률 상쇄된다.

정산 결과:

```text
진도믹스 → 30포인트 카드
골든리트리버 → 20포인트 카드
10포인트 카드는 미획득
```

### 4. 남은 보상 처리

살아남은 플레이어 수보다 보상 카드 수가 많으면, 지급되지 않은 보상 카드는 회수한다.

MVP 기본안:

- 미획득 카드는 보상 덱의 버림 더미로 이동
- 다음 라운드 시작 시 버림 더미를 다시 섞어 보상 덱에 포함 가능
- 미획득 보상은 어떤 플레이어의 점수에도 포함하지 않음

### 5. 모두 상쇄된 경우

밥그릇에 배치한 모든 플레이어가 동률 상쇄되면 누구도 보상을 받지 못한다.

예시:

```text
진도믹스 2개
푸들 2개
퍼그 1개
골든리트리버 1개
```

2개 동률 집단과 1개 동률 집단이 모두 상쇄되므로 모든 보상 카드를 회수한다.

## 라운드 종료

1번부터 6번 밥그릇의 정산이 모두 끝나면 라운드가 종료된다.

- 각 플레이어가 획득한 사료 보상 카드는 개인 점수 영역에 보관한다.
- 배치했던 주사위 8개를 모두 회수한다.
- 다음 라운드 시작 플레이어를 한 칸 이동한다.
- 6개 밥그릇에 새 사료 보상을 다시 배치한다.
- 총 4라운드를 진행한다.

## 경기 종료

- 4라운드 종료 후 각 플레이어가 획득한 모든 사료 보상 카드의 포인트를 합산한다.
- 가장 높은 점수를 얻은 강아지가 우승한다.
- 최종 동점이면 공동 순위로 처리한다.
- MVP에서는 별도의 타이브레이커를 두지 않는다.
- 결과 화면에서 순위, 총점, 상쇄 횟수, 가장 큰 단일 보상 획득량을 표시한다.

# 5. AI 봇

머신러닝이나 외부 AI API를 사용하지 않는다.

규칙 기반 휴리스틱 봇을 구현한다.

## 기본 평가 요소

AI는 선택 가능한 각 숫자에 대해 다음을 계산한다.

- 해당 밥그릇의 남은 보상 가치
- 선택 시 자신의 예상 순위
- 상대와 동률이 될 위험
- 상대를 상쇄시킬 수 있는 가치
- 사용하게 되는 주사위 수
- 남은 주사위 수
- 다른 밥그릇의 기회비용

## 난이도

MVP에서는 하나의 기본 난이도만 구현한다.

- 가장 높은 평가 행동을 대체로 선택
- 약간의 무작위 오차를 추가
- 항상 완벽하게 행동하지 않음
- 반드시 현재 주사위 결과에서 가능한 행동만 수행

AI 계산은 UI 코드와 분리해 순수 TypeScript 함수로 작성한다.

# 6. 이번 개발 범위

## 반드시 구현

# 7. UI 방향

## 화면 구성

### 1. Boot / Loading

- 단순 로딩 화면
- 게임명 표시
- 리소스 준비 후 자동 이동
- 실제 로딩보다 오래 붙잡지 않음

### 2. Home

- 게임명
- `게임 시작`
- `게임 방법`
- 임시 설정 버튼
- 최종 캐릭터 아트 대신 단순 플레이스홀더 사용 가능

### 3. Game

- 상단: 플레이어 4명의 얼굴, 이름, 현재 점수, 남은 주사위
- 중앙: 1~6번 밥그릇
- 각 밥그릇:
  - 번호
  - 보상
  - 플레이어별 배치 수
- 하단:
  - 현재 주사위 결과
  - 선택 가능한 숫자 버튼
  - 현재 턴 안내
- 동률 상쇄 시:
  - `KIBBLE CLASH!`
  - `동률 상쇄`
  - 어느 팀이 제외되었는지 텍스트 표시

### 4. Round Result

- 밥그릇별 정산 결과
- 상쇄된 플레이어
- 획득한 보상
- 다음 라운드 버튼

### 5. Match Result

- 최종 순위
- 획득 사료 포인트
- 상쇄 횟수
- 오늘의 임시 칭호
- `한 판 더`

## 디자인 원칙

- 최종 아트를 만들지 말고, 기능을 검증할 수 있는 깔끔한 그레이박스 UI를 만든다.
- 화면 크기 변화에 대응한다.
- Safe Area를 침범하지 않는다.
- 터치 요소는 모바일에서 충분히 크게 만든다.
- 색상만으로 정보나 상태를 전달하지 않는다.
- 모든 중요한 결과는 텍스트로도 표시한다.
- 애니메이션은 게임 진행을 막지 않아야 한다.
- 애니메이션 건너뛰기가 가능한 구조로 설계한다.
- 사운드가 없어도 게임 결과를 이해할 수 있어야 한다.

# 8. 아키텍처 요구사항

게임 규칙과 Cocos UI를 강하게 분리한다.

권장 구조:

```text
assets/
  scenes/
  prefabs/
  sprites/
  scripts/
    domain/
      models/
      rules/
      rng/
      ai/
    application/
      GameController.ts
      TurnController.ts
      RoundController.ts
    presentation/
      scenes/
      components/
      view-models/
    platform/
      apps-in-toss/
      storage/
    config/
      game-config.ts
tests/
docs/
```

## 핵심 원칙

- 게임 규칙은 Cocos의 `Node`, `Component`, `Sprite` 등에 의존하지 않는다.
- 주사위, 플레이어, 밥그릇, 라운드, 점수 계산은 순수 TypeScript로 작성한다.
- 동일한 시드에서 동일한 결과가 나오도록 Seeded RNG를 사용한다.
- 게임 상태를 하나의 명확한 모델로 관리한다.
- UI는 상태를 표시하고 사용자 명령을 전달하는 역할만 한다.
- 전역 mutable singleton 남용 금지
- 거대한 단일 `GameManager.ts` 금지
- 임시 데이터도 별도 설정 파일에서 관리
- 로직에 하드코딩된 숫자를 최소화
- 저장이 필요한 경우 추상화 인터페이스 뒤에 둔다.

# 9. 테스트 요구사항

도메인 로직은 자동 테스트를 작성한다.

최소 테스트 항목:

1. 지정된 시드에서 주사위 결과가 재현되는가
2. 지정된 시드에서 사료 보상 덱의 순서가 재현되는가
3. 각 밥그릇의 보상 합계가 최소 50포인트 이상이 될 때까지 카드가 배치되는가
4. 6개 밥그릇의 보상 카드와 총량이 주사위 배치 전에 확정되는가
5. 나온 숫자 중 하나만 선택할 수 있는가
6. 선택한 숫자의 주사위가 모두 배치되는가
7. 같은 눈의 주사위 중 일부만 배치할 수 없도록 막는가
8. 배치 후 남은 주사위가 정확한가
9. 주사위가 없는 플레이어의 턴이 건너뛰어지는가
10. 모든 플레이어의 주사위가 소진되면 라운드가 종료되는가
11. 같은 주사위 수의 플레이어가 모두 정산에서 제외되는가
12. 복수의 동률 집단이 각각 정확히 상쇄되는가
13. 상쇄 후 살아남은 플레이어 순위가 정확한가
14. 가장 높은 순위부터 가장 큰 보상 카드가 한 장씩 지급되는가
15. 한 플레이어가 같은 밥그릇에서 보상 카드를 여러 장 받지 않는가
16. 플레이어보다 보상 카드가 많을 때 남은 카드가 회수되는가
17. 모든 플레이어가 상쇄되면 아무도 보상을 받지 못하는가
18. 4라운드 점수가 정확히 합산되는가
19. 시작 플레이어가 라운드마다 순환하는가
20. AI가 불가능한 행동을 선택하지 않는가
21. 게임이 특정 상태에서 멈추는 무한 루프가 없는가

테스트 도구는 현재 Cocos 및 TypeScript 환경과 충돌하지 않는 범위에서 선택한다.

도구 선택 이유와 실행 명령을 README에 기록한다.

# 10. Apps in Toss 대응

## 작업 원칙

- 공식 Cocos 예제 프로젝트를 먼저 분석한다.
- 앱인토스 관련 코드는 `platform/apps-in-toss` 아래로 격리한다.
- 일반 브라우저 프리뷰에서도 게임이 실행되어야 한다.
- 앱인토스 API가 없는 환경에서는 안전한 fallback을 사용한다.
- 화면 방향 설정은 공식 예제 사용법을 따른다.
- 개발 중에는 샌드박스 테스트 절차를 문서화한다.
- 출시 체크리스트를 구현 단계에서 미리 반영한다.

## 이번 단계에서 할 일

- 앱인토스 개발 환경과 연결 가능한 프로젝트 구조
- Web Mobile 빌드
- 필요한 패키지와 스크립트 정리
- 로컬 프리뷰와 앱인토스 샌드박스 실행 절차 문서화
- 분석 이벤트를 나중에 연결할 수 있는 추상화 인터페이스

## 이번 단계에서 연결하지 않을 것

- 광고
- 결제
- 리더보드
- 리뷰 요청
- 공유 리워드

# 11. 독창성과 권리 관련 기준

이 게임은 특정 보드게임의 디지털 복제품으로 보이면 안 된다.

다음을 사용하거나 복제하지 않는다.

- `Las Vegas` 또는 원작 게임명
- 원작의 로고
- 원작의 설명문
- 카지노 디자인
- 원작의 지폐 그래픽
- 원작의 보드 레이아웃
- 원작의 색상과 아이콘 구성
- 원작 자산
- 공식 모바일 버전으로 오해할 표현

`주사위 결과를 선택해 구역에 배치하고, 동률이 상쇄되는 영역 다수 경쟁`이라는 추상적 구조를 바탕으로 독자적인 강아지 사료 게임을 만든다.

규칙 숫자, 보상 방식, 라운드 구성, 캐릭터, UI와 세계관은 프로젝트에서 독자적으로 관리한다.

# 14. 완료 기준

다음을 모두 만족해야 첫 번째 작업이 완료된 것으로 본다.

- 새 게임을 시작할 수 있다.
- 사용자와 AI가 정상적으로 턴을 진행한다.
- 사용자가 주사위 숫자를 선택할 수 있다.
- 선택된 주사위가 올바른 밥그릇에 배치된다.
- 동률 상쇄가 규칙대로 동작한다.
- 라운드 시작 전에 각 밥그릇에 총합 50포인트 이상이 되도록 사료 보상 카드가 무작위 공개 배정된다.
- 동률 상쇄 후 살아남은 플레이어가 주사위 수 순서대로 큰 사료 보상 카드를 한 장씩 받는다.
- 남은 사료 보상 카드는 회수된다.
- 4라운드가 진행된다.
- 최종 순위가 계산된다.
- 결과 화면에서 다시 시작할 수 있다.
- 자동 테스트가 통과한다.
- Web Mobile 빌드가 성공한다.
- 게임 진행 중 막히는 상태가 없다.
- 실행 방법이 README에 작성되어 있다.
- 플랫폼 관련 확인 결과가 `docs/platform-notes.md`에 기록되어 있다.

최종 그래픽 완성도는 완료 기준에 포함하지 않는다.

# 15. 작업 보고 방식

각 주요 단계가 끝날 때 다음 형식으로 짧게 보고한다.

```text
## 완료
- 실제 완료한 작업

## 확인
- 실행한 테스트와 빌드 결과

## 변경 파일
- 핵심 변경 파일

## 남은 문제
- 발견한 오류, 미확정 사항, 기술 부채

## 다음 단계
- 바로 이어서 할 작업
```

작업이 끝났다고 주장하기 전에 반드시 테스트와 빌드를 직접 실행한다.

실행할 수 없는 항목이 있다면 성공했다고 말하지 말고, 실행하지 못한 이유와 사용자에게 필요한 조치를 정확히 적는다.

# 16. 지금 바로 실행할 작업

위 요구사항을 기준으로 다음을 수행한다.

1. 현재 저장소와 개발 환경을 분석한다.

3. 계획 문서 5개를 작성한다.
4. Cocos Creator 3.8.7 기반 프로젝트를 준비한다.
5. 순수 TypeScript 게임 로직과 자동 테스트를 먼저 구현한다.
6. 플레이스홀더 UI로 한 판 전체가 가능한 그레이박스 MVP를 만든다.
7. Web Mobile 빌드를 검증한다.
8. 작업 결과와 실행 방법, 남은 문제를 보고한다.

범위를 벗어난 기능을 임의로 추가하지 않는다.

**최우선 목표는 예쁜 게임이 아니라, 반복 플레이하며 핵심 재미를 검증할 수 있는 안정적인 첫 버전이다.**
